# 全球资产市值看板 · BTC vs 黄金

每日更新的投资数据看板，横轴时间、纵轴市值，支持日 / 周 / 月 / 季 / 年五级 K 线。

后端 Python（FastAPI + SQLite），前端单页 ECharts，无需构建工具。

---

## 快速开始

```bash
cd /Users/kara/code/investment-dashboard
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m app.ingest --full          # 首次回填全部历史
.venv/bin/uvicorn app.main:app --port 8765     # 启动服务
```

打开 http://127.0.0.1:8765

## 1. 数据源

| 资产 | 行情来源 | 代码 | 历史起点 |
|---|---|---|---|
| 比特币 | Yahoo Finance | `BTC-USD` | 2014-09-17 |
| 黄金 | Yahoo Finance | `GC=F`（COMEX 黄金期货连续合约） | 2000-08-30 |

**为什么历史数据不走 CoinMarketCap**：CMC 免费版只提供实时报价，历史市值需要 Hobbyist 及以上付费套餐。
所以历史序列统一走 Yahoo Finance（免费、无需 Key、日线 OHLC 完整）。

如果你填了 `CMC_API_KEY`，每日抓取时会额外拉一次 CMC 官方 BTC 报价存入 `cmc_snapshot` 表，
用来校验下面自算供应量的偏差。**不填不影响任何图表功能。**

### 市值是怎么算出来的

行情 API 给的是**价格**，不是市值。市值由这个恒等式得到：

```
市值 = 当日价格 × 当日供应量
```

供应量不来自行情 API，而是各自建模（见 `app/supply.py`）：

**比特币** —— 按减半规则确定性推算已挖出总量。以 5 个已发生的减半区块高度和日期为锚点，
段内线性插值区块高度，段外按 10 分钟/块外推，再按每档 21 万块的区块补贴累加。
减半时点的结果与链上实际值完全一致（如 2024-04-20 恰为 19,687,500 BTC）。

**黄金** —— 你选的口径是「全球黄金总市值」，即地上黄金存量 × 现货价。
黄金几乎不被消耗，地上存量 ≈ 人类累计开采量。以 World Gold Council 的 2024 年底
216,265 吨为锚点，按历年矿产量逐年回推 / 外推，年内线性插值。

> ⚠️ 黄金存量是**估算值**，业界不同口径（WGC / GFMS / USGS）有 ±5% 的分歧。
> 但它年增仅约 1.6%，对曲线形状几乎无影响 —— 走势基本由金价主导。
> 要换口径改 `app/supply.py` 里的 `_GOLD_STOCK_2024_END_TONNES` 和 `_ANNUAL_MINE_OUTPUT_TONNES` 即可。

### 宏观指标

| 指标 | 来源 | 序列 | 频率 | 历史起点 |
|---|---|---|---|---|
| M2 货币供应 | FRED | `M2SL` | 月 | 1959-01 |
| 美国联邦债务 | 美国财政部 FiscalData | `debt_to_penny` | 工作日 | 1993-04 |
| 10 年期实际利率 | FRED | `DFII10` | 工作日 | 2003-01 |

两个源都**不需要 API Key**：FRED 官方 REST API 要注册申请 key，但它的 CSV 端点
（`fredgraph.csv?id=XXX`）可以直接下全历史，正好让整个项目保持零密钥、不必往 CI 里塞 secret；
财政部接口本身就是公开无鉴权的。

三个坑值得记一下：

- **单位不统一**：FRED 的 M2 以「十亿美元」计（`23155.2` = $23.16 万亿），债务是原始美元，
  利率是百分数。`config.py` 里每个指标带一个 `scale`，入库时统一换算成基准单位。
- **FRED 的缺失值有两种写法**：文档里说是 `.`，但 `DFII10` 实际用的是**空字符串**
  （23 年里 253 条，正好对应美国休市日）。解析时两种都要跳过。
- **财政部接口单页上限 10000 条**：目前全量 8371 条一页装得下，但再过几年就会超。
  代码里老实翻页，避免将来悄悄被截断只拿到前 10000 条。

宏观数据会被回溯修订，所以每次都全量重抓覆盖，不做增量。

## 2. 数据存储

SQLite，库文件 `data/market.db`。选它是因为每天每资产只有 1 行，全量约 1 万行，
时序数据库在这个量级上纯属负担。

**`daily_metrics`** —— 主表，主键 `(asset, date)`，抓取用 upsert，重复跑不会产生脏数据

| 字段 | 说明 |
|---|---|
| `asset` | `BTC` / `GOLD` |
| `date` | `YYYY-MM-DD` |
| `price_open/high/low/close` | 当日价格 OHLC |
| `supply` | 当日供应量（BTC 为枚，黄金为金衡盎司） |
| `cap_open/high/low/close` | 市值 OHLC = 对应价格 × supply |
| `volume` | 成交量 |
| `source` | 数据来源，如 `yahoo:BTC-USD` |

同时落库价格和市值，是为了让前端能自由切换两种口径，不必反算。

**`macro_series`** —— 宏观指标，主键 `(series, date)`，字段只有 `series` / `date` / `value`

宏观数据没有塞进 `daily_metrics`，因为它和行情根本不是一类东西：没有 OHLC（单值序列，
画不了蜡烛）、频率不统一（日频和月频混在一起）、且会被回溯修订。硬塞进去只能靠
`o=h=l=c` 这种糊法，不如单开一张窄表。

**`ingest_log`** —— 每次抓取的成功/失败记录，排查定时任务用
**`cmc_snapshot`** —— CMC 官方口径快照（没配 Key 则为空表）

### 周期聚合

只存日线，周/月/季/年在查询时聚合（`app/aggregate.py`），遵循 K 线惯例：
open 取区间首日开盘，close 取区间末日收盘，high/low 取区间极值，volume 求和。
数据量小，实时聚合毫秒级返回，省掉了预聚合表和它的一致性问题。
宏观单值序列则按区间末值取。

### 派生比值口径（市值 / 宏观指标）

「相对 M2」「相对联邦债务」这两个口径不落库，查询时算。关键是**分母要按「最近已知值」
对齐**而不是按日期精确匹配：M2 是月频且发布滞后约两个月，精确匹配的话绝大多数交易日都
取不到分母。`aggregate.AsOf` 用二分查找取不晚于当日的最后一个观测值。

分母在一天之内是常数，所以当日比值的 OHLC 可以由市值 OHLC 逐列相除得到；跨周期聚合时
在各日比值上取极值，分母的变动已经体现在每日比值里了。

## 3. 每日更新

抓取脚本是幂等的，同一天跑多次只会覆盖同一行。默认增量只补最近 10 天，
这样即使某天机器关机漏抓，第二天会自动补上。

```bash
crontab -e
```

加入（每天 08:30 跑一次）：

```
30 8 * * * /Users/kara/code/investment-dashboard/scripts/daily_update.sh
```

日志在 `logs/ingest.log`。手动补全部历史用 `.venv/bin/python -m app.ingest --full`。

> macOS 注意：cron 需要在「系统设置 → 隐私与安全性 → 完全磁盘访问」里给 `/usr/sbin/cron` 授权，
> 否则任务会静默失败。想避开这个坑也可以改用 `launchd`。

### 数据源限流与失败降级

三个上游都会限流，而且形式不一样：

- **Yahoo Finance**：直接返回 `Too Many Requests`
- **美国财政部**：**接受连接但不响应**，一直挂到超时，不返回 429。
  能成功的请求都在 3 秒内返回，被限流的则挂满整个超时时间。
  所以 `macro.py` 用「20 秒超时 + 6 次重试 + 递增退避带抖动」，
  而不是长超时少重试 —— 后者会把每次重试都浪费成一次完整的超时等待
  （实测 90 秒超时重试 3 次全部挂满，任务直接失败）。
- **FRED**：暂未遇到限流

失败时的降级行为是**有意设计成"整个任务失败"**的：

1. 抓取任何一个源失败 → `ingest` 非零退出 → workflow 该步骤中断
2. 于是 `export_static`、`git commit`、Pages 部署都不执行
3. GitHub Pages 保留上一次成功的部署，站点继续用前一天的数据

所以不会出现「半成品数据被提交」或「某个指标变成空白」的情况，代价是 Actions 里会看到一个红叉
—— 这正是希望被看到的信号。另外入库用的是 upsert，抓取失败只是没刷新，
不会破坏已有数据，第二天补上即可。

> GitHub Actions runner 的出口 IP 是和其他用户共用的，所以财政部接口的按 IP 限流
> 可能已经被别人占满。如果发现失败频繁，可以考虑让宏观指标失败不阻塞资产数据更新
> （代价是要处理"部分更新"的一致性）。

## 4. 前端

深色行情终端风格，`web/index.html` 单文件，ECharts 已下载到 `web/vendor/` 可离线运行。

- **资产**：勾选框多选，选项由 `/api/meta` 动态生成
- **周期**：日 / 周 / 月 / 季 / 年
- **口径**：市值 / 价格 / 相对 M2 / 相对联邦债务（按钮也是由 `/api/meta` 的 `value_modes` 生成）
- **叠加**：主图右轴可叠加一条宏观曲线（M2 / 联邦债务 / 实际利率）作对照
- **对数坐标**：默认开启。市值跨越 3 个数量级（BTC 从 50 亿到 1.2 万亿），
  线性轴会把早期完全压平，看长周期务必用对数
- **均线**：MA5 / MA20（按当前周期计算，仅单选时可用）
- **归一化**：仅多选时可用，见下
- 支持滚轮缩放、拖拽平移、十字光标 tooltip

顶部指标卡分两组：资产卡给出市值、涨跌、以及占 M2 / 占联邦债务的比例；
宏观卡给出最新值、同比和 sparkline。宏观数据有发布滞后，卡片上标出观测日期，
滞后超过 40 天的日期会转成琥珀色提示（M2 通常滞后约两个月）。

图表形态随勾选数量自动切换：

| 勾选 | 主图 | 副图 |
|---|---|---|
| 1 个 | K 线蜡烛图 + MA5/MA20 | 成交量 |
| 2 个 | 两条市值曲线叠加 | 两者市值比值 |
| 3 个及以上 | 多条曲线叠加（占满全高） | 无 |

至少要保留一个勾选，取消到最后一个时该项会被锁定，避免图表空白。

**归一化**解决的是多资产量级悬殊的问题：BTC 市值 1.26 万亿、黄金 31.8 万亿，直接叠加只能看出
"一条在上一条在下"。勾上归一化后，会找到**所有选中资产都有数据的第一个时间点**作为共同基准，
各自置为 100，于是比的是相对涨幅 —— 以 2014-09 为基准，BTC 现在是 24,790（约 248 倍），
黄金是 455（约 4.5 倍）。tooltip 里仍会同时给出归一化值和真实市值。

两个资产时的比值曲线比两个绝对值更能说明问题：现在是 3.98%，即比特币市值约为黄金的 1/25。

黄金周末休市而 BTC 全年无休，所以日线下黄金无周末数据；曲线以时间轴并集渲染、缺口连线，
比值曲线则只取两者都有数据的交易日。

**相对 M2 / 相对联邦债务**是这个看板加宏观数据后真正有意义的部分——它回答的不是
"BTC 涨了多少"，而是"硬资产相对整个法币体系值多少"。当前黄金市值是 M2 的 137%、
BTC 是 5.5%；换成联邦债务做分母则是 80% 和 3.2%。

宏观叠加线用**前向填充**对齐到图表时间轴（取不晚于当日的最后一个观测值），
否则月频的 M2 画在日线图上会是一串孤立的点而不是一条线。

## 接口

静态部署下这些接口对应 `web/data/` 里的预生成 JSON（见 `app/export_static.py`），
本地跑 uvicorn 时是动态接口，两者输出逐根一致。

| 接口 | 说明 |
|---|---|
| `GET /api/meta` | 资产与宏观元信息、数据范围、可用口径、最近一次抓取状态 |
| `GET /api/klines?asset=BTC&period=month&value=cap` | K 线数据，`value` 可选 `cap`/`price`/`per_m2`/`per_debt` |
| `GET /api/ratio?base=BTC&quote=GOLD&period=month` | 任意两资产的市值比值序列 |
| `GET /api/macro?series=M2&period=month` | 宏观单值序列 |
| `GET /api/summary` | 最新市值、涨跌、资产间比值、宏观最新值与 sparkline |

## 加新资产

前端不用动 —— 勾选项、配色、卡片都是从 `/api/meta` 生成的。只需两步：

1. `app/config.py` 的 `ASSETS` 里加一条（代码、中文名、Yahoo ticker、颜色）
2. `app/supply.py` 里写该资产的供应量函数，注册进 `SUPPLY_FN`

然后 `.venv/bin/python -m app.ingest --full` 回填即可。

难点从来不是行情（Yahoo 上白银 `SI=F`、铂金 `PL=F`、以太坊 `ETH-USD`、
威尔希 5000 `^W5000` 都能直接取到），而是**供应量怎么建模**：

- 白银 / 铂金：会被工业消耗，"地上存量"比黄金模糊得多，得先定口径（累计开采量？还是仅存世条块？）
- 以太坊：PoW 发行 → 2022 合并 → EIP-1559 销毁，没有 BTC 那样的闭式公式，需要历年供应量锚点插值
- 股票指数：指数点位不等于市值，需要额外的股本/换算因子数据源

## 加新宏观指标

同样前端不用动。在 `app/config.py` 的 `MACRO` 里加一条：

```python
"CPI": {
    "name_cn": "CPI 通胀", "short_cn": "CPI",
    "source": "fred", "series_id": "CPIAUCSL",
    "scale": 1.0, "unit": "index", "freq": "monthly",
    "color": "#e5c07b",
    "denominator": False,   # True 则自动多出一个「相对 CPI」口径
    "note": "月频，发布滞后约两周",
}
```

`source` 目前支持 `fred`（走 CSV 端点）和 `treasury`。设 `denominator: True` 会自动
生成对应的派生口径按钮、静态 JSON 和卡片上的占比，不需要改任何前端代码。

第二、三层还没做的候选指标：美联储资产负债表 `WALCL`、10 年期盈亏平衡通胀率 `T10YIE`、
广义美元指数 `DTWEXBGS`、核心 PCE `PCEPILFE`。加之前建议先用 CSV 端点拉一次核对，
FRED 偶尔会停更或重命名序列。
